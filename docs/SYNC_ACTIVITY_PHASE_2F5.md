# Phase 2F.5 — 当前任务可见与按编号取消

基于 449105db / 4.189.0 / schema 13。本阶段将 2F.4 的取消链路接到实际界面，不改变数据库、恢复记录格式、锁租约、manifest 发布或事务算法。

## 实际入口

- RecoveryRunner 为手动同步、自动同步、连接检查、预演、自动同步启用验证及冲突处理注册随机 128 位任务编号。
- GET /api/sync/activity 只读取内存快照，不读取 SQLite 或任务文件、不等待执行闸门。字段限定为 active/id/kind/phase/started_at/cancel_requested。
- POST /api/sync/cancel 必须携带完整 id。只给匹配的当前任务发送 context 取消信号；缺少或无效编号被拒绝，已结束/过期编号返回 accepted=false。不存在“取消最新任务”的无编号快捷路径。
- 重复请求同一个仍在运行的任务是幂等的；旧任务的取消、结束及阶段更新不能影响后续任务。
- accepted=true 只表示已发出信号，不表示任务已结束、写入已撤销或清理已完成。注册在任务与恢复记录处理返回后才移除。

## 界面行为

同步中心新增独立“当前同步任务”卡片。即使主面板因正在保存/同步而暂停数据库状态读取，任务卡仍可读取内存状态并请求取消。

活动任务或当前有界面操作时，读取成功后的间隔为 1 秒，空闲为 5 秒。请求有 5 秒期限，单飞、卸载清理、迟到响应作废及 30–300 秒读取失败退避沿用同一个状态读取器；没有 setInterval 重叠请求。原主面板的正常 15 秒周期不变。

取消须确认，并固定使用点击时的任务编号。只发送一次 POST；请求超时显示“取消结果尚未确认”，不自动重复发送。已接收取消后，旧的读取响应不能把同一任务按钮重新启用。旧取消响应也不能把新任务显示成正在取消。

观察到任务离开活动列表后，再通知主面板刷新恢复信息；主面板仍忙时由其原操作结束路径负责刷新。冲突处理失败也补充刷新恢复记录。

## 保守边界

- 只读预检取消不进入写入阶段；进入可能写入阶段后取消，继续保留 applying/review_required，不自动重跑，不宣称回滚。
- 取消仅影响本次任务，**不关闭自动同步开关**。只读预检取消后，调度器后续仍可能再次运行；需要停止后续计划应使用暂停自动同步。
- 任务注册只保存在当前进程内，重启后恢复判断仍依赖 2F.3 的持久化记录。空闲快照不证明上次提交成功。
- 不强制终止进程，不取消 Electron 凭据保存/重启、设置写入或重新绑定；本地磁盘/计算的协作式取消限制、框架 HTTP 响应期限和应用退出顺序未在此改动。
- 这是本机单个受管后端的任务控制，不是新增用户鉴权、分布式锁或跨设备取消。

## 验证

本地 12 项实际 ActivityTracker 标准库测试通过，race 开启重复 20 轮，go vet 通过；独立 Windows 测试二进制跨编译通过，未在本地运行 Windows 二进制。

本地 11 项 Node 测试通过，覆盖实际取消请求辅助函数、编号捕获、拒绝确认、不自动重放、响应校验、状态读取周期、单飞和卸载。JSX 转译检查只证明语法，不视为 React 运行通过。

新增 4 项使用仓库真实 SQLite/HTTP fixture 的 Runner 集成测试，覆盖预检取消、数据库占用期间取消、可能写入阶段保留 Review、迟到编号隔离及取消自动同步启用验证。新增 9 项 React 界面测试并明确接入 CI；保留原有组件测试。当前本地无法联网取得完整仓库依赖，这些整合测试由 CI 执行，不把本地子集测试称为完整应用验收。
