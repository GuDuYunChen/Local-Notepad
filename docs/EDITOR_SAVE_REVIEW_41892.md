# 4.189.2 保存回执与冲突恢复复查

基线：8480c91d293fbdb1f565da2d710536b1edefd4dd（4.189.1 / schema14）。本轮修复上一阶段遗漏，不开发下一功能阶段，继续原分支与 Draft PR #2，不合入 master。

## 复现的遗漏

1. 成功确认正文后仍留下带新编辑时间的缓存；250ms 延迟回调也会再缓存已保存正文。若引用维护等在同一秒更新数据库，秒级 updated_at 与毫秒级缓存时间比较可让旧的已保存缓存遮住新正文。真实 TextEditor 回归在精确旧代码失败，修复后清除匹配的已保存缓存，并让延迟回调再次检查正文是否仍未保存；保留等待期间新编辑的草稿。
2. 预期数据库正文不匹配时，旧后端仅返回普通错误。前端一直保留并重发同一个旧预期请求，也没有明确的冲突处理入口。新协议将这种判断持久化为“已拒绝且不会写入”的终局回执，而非超时；前端保留草稿、停止自动重复提交，并提供可核对的处理入口。
3. 旧请求回执重放返回的是原请求正文，即使数据库已经有更新的正文。回执证明过去提交过，不证明当前数据库仍是它。复查使用上一轮精确后端二进制启动隔离数据库：先写第一版、再写新版、重放第一版，旧行为返回第一版。本轮回执携带 applied/conflict/superseded 结果，并在同一数据库写预留内读取当前正文，过时回执不能将草稿标成当前已保存。

## 冲突恢复

“处理保存冲突”展示草稿和数据库正文的文字预览（各最多1600字符，不改变保存格式）。用户可以暂不处理、采用数据库正文，或保留我的正文。默认焦点在取消，支持 Escape 与 Tab 焦点约束。

保留我的正文只对用户刚核对的数据库正文发起新的比较写入；若数据库再次变化，仍拒绝覆盖并重新提示。真正替换时，原数据库正文进入既有版本历史（最近50条），不是永久备份。

采用数据库正文明确放弃当前草稿，先重新读取并核对文档、加载代次和草稿是否变化；核对期间的任何新编辑不被晚到读取覆盖。该操作不写数据库。无法核对则保持草稿和冲突提示。

被拒绝的请求编号持久化后，即使数据库后来恢复为旧预期正文，该旧编号也不能突然成为一次写入。利用 schema14 已有的 obsolete 状态和带标记的元数据保存拒绝结果，旧4.189.1后端也会保守拒绝此编号；无需新增迁移。真正的取消/网络超时仍是未确认状态，不清除请求编号、不允许静默放弃。

## 边界与验证

版本4.189.2，数据库仍为 schema14；前后端共同升级。新前端不接受缺少明确 outcome 的旧服务器回执。安装前备份工作区和当前未确认正文。本轮不声称能解决损坏数据库、所有引用歧义、跨进程强制结束后的每种恢复情形；也没有删除退出保护或自动选择覆盖。

新增组件回归覆盖已保存缓存、终局冲突停止重试、两种显式决策、再次并发修改、晚到采用请求、相同正文仍有冲突、取消/Escape与文本转义。协议测试拒绝过时/缺失结果；SQLite测试覆盖终局拒绝持久化、回滚与兼容性；实际 App + HTTP + SQLite 重启测试补充冲突决策、版本历史和终局请求跨重启不写入。

精确旧版本失败证据与新提交通过证据分开保留。现有自动保存/退出/放弃草稿、完整UI与Go、Windows构建和打包应用检查仍需对新提交全部验证；不能借用8480c91的成功记录。
