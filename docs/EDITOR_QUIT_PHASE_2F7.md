# Phase 2F.7 — 退出前正文保存握手

基于 4ddc36b4 / 4.189.0 / schema 13。不改变同步协议、恢复记录格式、数据库 schema 或 backend drain 算法。

## 本轮先修复的既有 CI 问题

上一阶段 PR CI #1210 的 backend tests 在 TestRecoveryShutdownCancelsHTTPAndPreservesCheckpoint/preflight 中卡住，最终超时，不能视为上一阶段已全部验收。该测试的 HTTP handler 未消费 PROPFIND 请求体就等待请求 context；客户端取消并返回后，测试服务端仍可能无法观察断连，httptest.Close 因而一直等待。

本提交在等待断连前消费测试请求体，并增加测试清理通道；原有 runner 排空和恢复记录断言保留，额外断言测试服务端观察到取消。不是跳过测试、延长 CI 超时或削弱正式取消逻辑。本地标准库对照复现验证了旧未读请求体阻塞和修复后取消两个场景；真实 SQLite/Runner 集成仍以 CI 为准。

## 退出顺序

1. X / Alt+F4、菜单退出和正常 app.quit 在销毁当前窗口之前被拦截。macOS 仅关闭窗口也先保存，但仍保持应用驻留的既有行为。
2. Electron 给当前窗口当前 main frame 发随机 128 位挑战。只有相同 webContents、main frame、挑战编号和布尔 ready 响应有效。迟到响应、子 frame 和其他窗口不能批准本次退出。
3. Renderer 检查是否有尚未确认的输入法组合文字；若有，拒绝退出且不先改变焦点。否则锁定编辑区域，显示保存中的遮罩，阻止保存确认后继续键入。
4. 通过 TextEditor 原有保存队列等待已发送保存，然后保存尚未发送的当前正文。确认返回的文档 ID 和内容均匹配，且当前快照没有再改变。
5. Renderer 回复 ready 后仍保持输入锁定。Electron 此时才运行 2F.6 的后端排空/退出确认流程。
6. 保存失败、正文切换/加载、尚未确认的结构改动、源码草稿或超时，均返回编辑；不会发送后端关闭命令。后端停止失败也释放遮罩并保留窗口，不能假称退出完成。

Renderer 等待预算 8 秒，主进程确认预算 10 秒；超时不批准退出。已经发送的正文写入不会因为 UI 等待超时被当作已撤销；用户应等待/检查状态后重试。没有加入“保存失败也默认强退”的路径。

## 草稿及保存响应

- Renderer 维护本次会话中实际观察到的正文草稿账本。不通过 IPC 发送正文、文件路径或缓存列表，只回复挑战编号和固定结果码。
- 仅相同文档且匹配最新内容的确认可清除账本项。旧保存响应不会清除较新草稿，也不会用旧内容覆盖较新的草稿缓存。
- 较旧的不同正文正在保存时，即使用户把文本改回原基线，也要先等旧写入结束再决定是否保存，不能提前将回退操作当成无需写入。
- 编辑器卸载不会删除未确认草稿账本。此前切换走且保存失败的笔记会阻止退出，需返回对应笔记确认；不批量覆盖缓存中的旧笔记。
- 明确删除的文档可移除对应账本项。已有手动保存与结构重构确认流程继续使用。
- 章节标题/层级有待确认变化时，退出不绕过 Ctrl+S 的引用影响确认。已打开的 Markdown 源码编辑面板有未应用修改时，也不默默应用或丢弃。

## 明确边界

这是正常窗口/应用退出前的正文握手，不保证系统强杀、断电、renderer 崩溃、开发工具强制导航/刷新、磁盘异常时保存成功。无法取得 renderer 确认时保留退出失败提示，不将缓存称为数据库持久化。新逻辑没有提供跨设备并发版本比较或断电 fsync 保证。

草稿账本针对 TextEditor 正文和本次会话观察到的未确认笔记；不扫描旧会话所有 localStorage，也不覆盖其他独立配置对话框的未提交字段。Markdown 面板自己先前被关闭/丢弃后的行为未重写。安全凭据保存或后台进程重启路径不借此新增自动正文批量保存。工作区恢复与同步不确定写入仍保留原有规则。
