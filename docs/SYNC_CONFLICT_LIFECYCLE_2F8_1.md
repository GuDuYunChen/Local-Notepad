# Phase 2F.8.1 — 冲突生命周期与失效确认修复

## 复核结论

基线 `e4e8bdb91f3e639fad73a70b47e1ad0b5764f764` 的 push #1223 两个任务均已成功。继续审查发现三处原测试没有覆盖的生命周期问题，本阶段先修复，不叠加下一阶段业务功能。

1. **冲突消失**：旧逻辑由对象 ID 和三端哈希生成固定冲突 ID；A → B → A 时，A 已被标为 superseded，INSERT OR IGNORE 又不重新创建 A，最后待处理列表为空，但计划仍报告冲突。本地使用原始 SQL 在 SQLite 中复现，待处理数量依次为 1、1、0。
2. **过期冲突滞留**：用户另行编辑后，两端已经一致，或者已变为正常上传/下载，成功执行同步仍未退役以前的 open 快照，导致状态与列表不一致，后续自动同步继续被旧冲突挡住。
3. **旧确认恢复有效**：前端只比较当前快照与捕获快照是否相等。对照已经观察到版本或目标变化，之后又恢复原值时，旧确认可能重新变成可提交状态。失效必须是单向的，不能因为数据恢复原样而恢复授权。

## 修复

新产生的 open 生命周期分配独立的 32 位十六进制随机 ID。只有同一对象、同一 base/local/remote 哈希且仍为 open 的记录才复用原 ID。已有旧版固定 ID 的正常 open 记录保持不变；已解决或已被替代的历史记录不覆盖、不重新启用。旧 ID 的迟到请求不能处理新的冲突实例。

替代旧记录与插入新记录沿用同步事务；独立 storeConflict 入口也包裹事务，插入失败时不会只退役旧记录却没有可处理的新记录。上传、下载或无变化项在同一成功事务内将过期快照标记为 superseded，不伪造用户的 local/remote 决定。只读预演不修改冲突。失败或外层回滚保留原冲突、原基线和已发布的远端 manifest。

前端增加单向失效 guard。在 React 已提交的界面状态中观察到快照或目标变化，立即清除确认并锁定旧对照；即使 A → B → A，仍须点击重新对照。新对照创建独立 guard，不复活旧请求。普通的同内容刷新不强行清除用户已选方向。提交前追加 AbortSignal 终检，已停止的读取不能在发送前的边界继续写入。

## 不变项与边界

继续 `feature/knowledge-os-phase2`，PR #2 保持 Draft，不合入 master。版本 4.189.0、数据库 schema 13、同步对象/manifest 格式、凭据存储和既有退出/恢复规则不变，不删除历史冲突记录。冲突 ID 仍是相同格式的 opaque ID，但现在区分生命周期。

这是生命周期缺陷修复，不是新增服务端原子确认协议、自动合并、断电回滚保证或新同步 provider。已经存在的错误历史无需修改：下次手动执行同步会依据当前真实版本生成新的可处理实例，或在成功收敛后退役过期实例。
