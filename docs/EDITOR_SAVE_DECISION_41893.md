# 4.189.3 — 保存冲突决策与读取生命周期修复

基线：`ca9259c21ae0518b6d4f44d21bd7d48a232fedd7`（4.189.2 / schema14）。本轮是对上一阶段的复查和修复，不进入下一功能阶段，继续 `feature/knowledge-os-phase2` / Draft PR #2，不合入 master。

## 复查结果与可复现问题

上一轮结构自动保存、独立引用维护、终局回执和缓存修复继续保留。新检查发现三个遗漏：

1. **“保留我的正文”在相同正文时绕过数据库比较。** 冲突发生后，编辑器会记录上次观察到的数据库正文。若草稿恰好改成相同正文，显式保留操作删除冲突状态后进入普通“无变化”快捷返回，没有再次提交条件写入。数据库此时再次变化，仍可能把草稿当作已保存并释放退出登记。
2. **采用数据库正文的迟到读取可以在卸载后清除草稿。** 原来的加载代次只在切换/重载时递增，整个编辑器卸载未使它失效；采用操作的只读请求也未被退出清理管理。迟到响应仍可能通过检查，清掉已缓存草稿及未保存登记。
3. **采用失败的原因留在弹窗背后的状态栏。** 弹窗仍开启且主页面不可交互，弹窗自身却没有失败反馈。用户无法在当前操作位置区分失败与继续等待。

四项针对性的真实 TextEditor 断言在精确4.189.2源码上失败，原八项测试仍通过。基线验证器校验旧两个产品文件的完整Git blob摘要；导入错误、超时不能当作缺陷复现。

## 修复边界

- 显式冲突保留强制进入原有比较写入，即使草稿与上次看到的数据库正文相同；只有实际 applied 回执可以释放该次状态。普通干净笔记的保存仍不发请求。再次发生并发修改时保留草稿和冲突，绝不静默覆盖。
- 采用操作使用独立 AbortController；切换或卸载时中止其读取并使加载代次失效。即使传输层忽略中止、返回迟到响应，也不能改变草稿或退出登记。旧操作的 finally 只能释放属于自己的忙碌状态。
- 失败/超时在仍开启的冲突弹窗内显示可访问提示，保留重试与取消，错误原文不在该提示中展示；重新打开或重试会清除过时的失败信息。没有自动选择版本或新建普通保存确认步骤。

正文保存协议、Go后端、独立引用维护和数据库结构均未改，仍为schema14。版本升级到4.189.3以区分安装包。真正未确认的正文、源码未应用、输入法组合和后端退出保护仍保留。

## 新增回归

原8项冲突组件测试保留，新增7项：同正文但数据库再次变化、同正文的实际成功回执、卸载后的迟到采用、弹窗内失败提示、8秒超时后重试及旧响应、切换文档中止、失败后取消并重新打开。

原6项真实App/TextEditor + Go HTTP + SQLite场景保留，新增2项：

- 使用实际数据库制造同正文冲突，再次修改数据库；第一次保留必须被拒绝且退出握手不能批准。随后明确采用数据库正文，退出与父管道正常关闭、服务重启后验证正文。
- 采用请求已取得实际HTTP响应但延迟交付，卸载后再释放；草稿仍保留。重新打开继续保存、退出、重启并直接读取数据库核对最新正文。

这些测试使用隔离数据库和可控富文本输入/导航夹具，不是用户现场，也不是物理键盘或完整Electron窗口端到端测试。未改变Go后端时，本地集成使用上一轮摘要核对的实际服务器；最终CI仍会从新提交重编译并执行全量Go及双平台真实服务检查。
