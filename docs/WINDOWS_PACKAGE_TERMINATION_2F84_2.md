## 原问题与复现

旧runNative在超时/取消时，只要直接子进程exitCode或signalCode已赋值就返回；但Promise要等close事件，而继承输出管道的后代进程可以使close持续等待。确定性真实Node子进程复现：300毫秒超时或取消已发生，约1.45秒后仍得到exitCode:0的成功结果。五个新增相关回归在精确旧模块上全部失败。未操作用户进程或真实笔记，隔离后代有自行退出上限。

Node官方文档明确区分exit和close，后者等待stdio关闭，多个进程可共享这些流。参考：https://nodejs.org/api/child_process.html#event-close 。这不是已确认的ChatGPT平台断流原因。

## 本次完成范围

保持bat/PowerShell入口、环境和版本检查、npm ci、旧安装包隔离、实际构建、准确EXE/PE/SHA256和日志交付路径。新增的处理覆盖从取消/超时发生到失败回执、进程清理和下一次启动保护，而非只调整一条提示。

- 超时与取消持续有效直到命令及输出关闭，直接父进程退出不能使其失效。迟到的正常退出不再改写已取消或已超时结果；close回调也复核单调截止。
- POSIX使用本次自有进程组发送终止及必要的强制终止；Windows仅针对仍存活的本次子进程调用系统taskkill /t /f。不会对已退出、可能被复用的父PID重新发终止命令。
- 清理预算默认5秒，包含终止辅助进程等待。预算耗尽时停止等待、断开本轮持有的管道并明确标记cleanupUnconfirmed，不能报告干净成功。停止后迟到输出不再写入本次日志。
- Windows父进程已退出、后代仍占用管道时，现有PID不能证明后代归属。此时明确报错，不冒称已经杀掉所有后代，并保留running.lock。失败回执记录原阶段、原因、进程标识和recoveryRequired；下一次启动拒绝抢锁，不启动新的安装或构建。
- 确认干净结束的普通失败仍释放锁。原保存/退出保护、报告功能、依赖节点和数据库不改，所有既有测试/工作流保留。

## 失败后的实际操作

出现“process cleanup unconfirmed / packaging lock retained”时，先打开错误中的本次日志目录，核对running.lock与receipt.json。确认该次npm、构建工具及其后代都已退出后，才删除该仓库的test-results/local-package/running.lock并重新执行pack-win.bat或pack-win.ps1；不能仅因父PID已消失就认为所有后代已退出。不要删除依赖锁或用旧EXE代替新产物，不自动重试、不自动清除不明锁。正常成功使用方式不变。

清理上限是事件循环可运行时的预算，不保证操作系统强杀、断电、阻塞系统调用或恶意构建脚本下的原子取消。本工具不是任意恶意子进程的沙箱；不确定时拒绝交付，而不是宣称进程已全部消失。
