# Phase 2F.13.1 — 浏览操作即时撤销旧确认

## 复查发现

复核基线 `f7e26742a30582e722a6846408997fe65ba5fb04`，PR #2 仍为 open/Draft、分支 feature/knowledge-os-phase2。前一提交的 CI 成功不代表没有未覆盖的事件次序。

队列原先只在 `setBrowse` 的状态更新提交后，通过新的行 key 卸载旧对照。先触发浏览，再在同一批次、重渲染前调用旧卡片确认时，父级 resolver 没有核对浏览代次，可能把已撤销的确认传给处理回调。原有“先提交、后排序”测试验证的是相反次序，不能证明这一路径被阻止。

本地使用 Git blob SHA 匹配的原始 Queue（`c80b606959a60333ec0859b51242464245678237`），执行实际 change/resolve 函数并延迟 setBrowse：一次浏览之后，旧 resolver 仍被调用一次。这是处理函数级复现；不是声称普通用户每次点击都会触发，也不是已经造成数据库损坏的证据。后端的重读、版本/事务保护未被改动。

## 修复

新增仅在当前组件内存中的同步浏览代次 ref。浏览意图被接受时立即递增代次，再提交新的显示状态；旧渲染中的 resolver 必须与同步代次一致，才允许进入 onResolve。代次递增不放进 React 状态 updater，避免 updater 重放带来副作用。

搜索、类型/关注项筛选、清空筛选、排序和全部分页入口共用此保护。A-B-A 不恢复旧确认；先提交后浏览仍被既有 pending ref 拦截。相同快照的普通刷新不增加浏览代次，不无故撤销有效确认。新视图中明确重新对照、勾选后可以正常提交。额外检查组件存活状态，已卸载组件保留的回调不能再启动处理。

## 新增验证

- 14 项 Node 实际回调测试：浏览先行、旧闭包跨渲染、A-B-A、updater 重放、提交先行、原参数、禁用/失效/卸载、失败解锁；延迟状态调度是测试夹具，不冒充完整 React。
- 15 项真实 Queue + Review React 场景：9 个浏览入口先行、同批次 A-B-A、重新对照、相同刷新、提交先行、StrictMode、只读浏览。
- Linux 独立基线脚本：下载固定提交原始 Queue 并校验 Git blob SHA；在隔离临时文件中配合真实 Review 运行新增 React 断言。要求四个分页事件先行的断言以“旧 resolver 被调用”的原因失败，编译错误、缺失报告、超时、其他失败不算复现。修复版专项随后独立运行。
- Windows 追加修复版 Node/React 专项；每条命令核对 LASTEXITCODE。所有旧步骤、测试、相对顺序和超时预算保留，原生截图及打包检查继续执行。
