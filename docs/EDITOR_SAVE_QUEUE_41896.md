# 4.189.6 — 连续保存的顺序、完成提示与退出登记

基线：`3c66a5e36189c5876fb8c1e21fd66c7d1d09f19a`（4.189.5 / schema14）。继续 `feature/knowledge-os-phase2` / Draft PR #2，本轮只修复上一阶段，不开始其他功能或合入 master。

## 已复现的根因

原队列仅记住正在发出的请求，不记住最后一个已排队的保存意图。先提交正文 A，在其回执尚未返回时提交 B，再把正文改回 A 并保存，最后一次 A 会因为与正在执行的 A 内容相同，直接复用第一笔请求。随后已经排队的 B 继续写入，最终数据库变成 B。A→B→C→B 也有同类问题；定时自动保存与 Ctrl+S 混合时同样会发生。

因此有三项用户可见后果：最后一次保存的内容不是最终数据库正文；较早的成功回执可能让应用提前显示“正文已保存”；若最新可见正文恰好被第一笔回执确认，登记会被清除，后续排队写入再次令它未确认时却没有重新登记，卸载编辑器之后退出检查可能遗漏这份草稿。

不是数据库事务重试协议失效，也不是需要增加章节确认。问题发生在同一个编辑器的前端请求排序与保存完成判断。

## 修复边界

每篇笔记分别维护最后排队的请求，按发起顺序连接到同一条现有保存路径。只合并相邻且正文相同的保存；最后一个请求与较早正在执行的正文相同，但中间还有不同正文时，必须等待中间保存并再次比较后写入。排队时捕获本次请求的正文，不擅自把用户后续尚未要求保存的编辑混进去。原协议仍为每次实际写入生成不可变编号，未知结果重试继续使用原编号；本次没有修改 Go 后端。

退出等待和显式放弃检查包含队尾；每次真正发出 PUT 前，按当前有效正文或原文档恢复缓存，重新建立未确认登记。第一笔回执不再让后续写入失去保护。队列中的旧请求失败后，不自动执行后面的新写入；原草稿和重试信息保留。卸载仍先撤销生命周期权限再取消请求，队列不会在卸载后启动新 PUT。

App 在得到某一笔成功回执后，还检查该笔记是否有正在进行或排队的保存。仍有待完成请求时，提示“仍有正文保存正在排队”，不会宣称已全部保存或批准“保存后继续”；最后一次确认后才显示完成。

普通自动保存、Ctrl＋S、不保存和保存冲突选择没有增加新按钮或章节审查。后台引用维护、缓存格式、源码/输入法保护、同步、后端事务和 schema14 不变。版本4.189.6，无数据库迁移。

## 最后复查补齐隐藏笔记缓存

首个队列修复提交`ca0a71f`通过原候选与专项后，进一步复查发现：笔记已切走时，较早的A回执会删除与其相同的可见草稿缓存，下一笔B只能使用排队快照回填，丢失用户尚未要求保存的回退A。中间B失败时也有同类风险。因此首个构建不作为最终交付。

只要这篇笔记还有队列尾部，较早回执即使与草稿相同也不删除缓存；后续请求继续携带真实最新草稿。只有队尾已经结束、原编辑器生命周期仍有效、没有活动请求/未确认请求/冲突、并且缓存正文与当前已确认数据库正文相同，才清掉匹配缓存。真实未保存的可见回退保留，已全部确认的A→B→A也不会产生多余草稿。新增3项组件断言和2项真实服务场景；最终提交必须重新完成全套验收，首版的通过不代替最终结果。
