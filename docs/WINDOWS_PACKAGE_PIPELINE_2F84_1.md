## 问题

旧 pack-win.ps1 的原生 npm 命令没有退出码判断；node_modules 存在便跳过安装，且构建后递归搜索任意 EXE。失败后可能把上次安装包或 win-unpacked 中的程序误报为本次成功。README 提到的 pack-win.bat 在当前提交中不存在，环境要求、安装命令与产物目录部分说明过期。这些问题没有由此前直接调用 npm run build 的 CI 路径覆盖。

## 完整操作路径和结束条件

Windows 上双击根目录 pack-win.bat，或从任意目录执行 pack-win.ps1。-NoOpen 仅抑制成功后打开资源管理器，不跳过安装和校验。入口显式传播非零退出码，命令失败不再继续输出成功。

1. 检查 Windows、Node.js 22.12+（CI 使用24）、项目版本与完整 lock；检查 npm 和 server/go.mod 指定的有效 Go 工具链（当前1.24.11）。
2. 获取本仓库唯一打包锁，始终执行 npm ci --no-audit --no-fund，即使已有 node_modules；安装后核对 manifest/lock 原始字节未变。尊重用户原有镜像环境，不写入、覆盖或输出环境中的凭据。
3. 仅隔离 release 下同版本的旧安装包及其摘要到本次日志目录，不删除其他版本、工作区或笔记。执行原 npm run build，完整构建 Go 后端、Electron、渲染页面和 NSIS。失败立即终止，不自动重试或回退旧产物。
4. 只接受本次生成的 release/Notepad-<version>-Setup.exe。沿真实 PE 的 RT_VERSION 资源读取文件/产品版本，必须与 package.json 的版本加 .0 一致；拒绝不存在、空、损坏、旧版、重定向产物。不搜索任意 EXE，不根据名称猜测内部版本。
5. 成功输出准确路径、SHA-256、旁路 .sha256 文件及本次 JSON 回执。完整命令日志与失败阶段保存在 test-results/local-package/<本次运行>/；该命令只打包和核验，不自动安装、运行应用或访问真实用户笔记。CI 仍执行原完整安装/运行/卸载校验。

## 失败和取消

Ctrl+C 会请求停止本轮子进程，命令超时或终止都不能形成成功回执。运行锁防止同目录重入。系统强杀或断电可能留下 running.lock：先检查记录中的进程与任务管理器，确认没有打包进程后才手动删除该锁，再重新执行；不得自动抢占不明锁。任何失败都查看本次日志的首个错误，修正原因后明确重试，不反复删除依赖锁或改用 npm install。已有旧包保留在日志目录，不冒充新包。

源码目录的代码和 npm 生命周期脚本本就具有构建权限；本入口不是恶意仓库沙箱，不保证其他进程并发修改源码时可安全交付，也不能解决断电或系统强杀。版本校验不等于代码签名、用户机器现场安装或全平台验收。
