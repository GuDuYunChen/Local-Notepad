# 4.189.4 — 重新打开未确认草稿时保留正文、基线与原请求

基线 `5cf6619336554b4e8af6320ba41e03344f4db0dd`（4.189.3，schema14）。继续 `feature/knowledge-os-phase2` / Draft PR #2。本轮只修复上一阶段遗漏，不进入下一功能阶段，不合入 master。

## 已复现的问题

复查不只看“保存成功后退出”，还覆盖“保存尚未确认时离开，再重新打开”：

- 五分钟缓存有效期或较新的数据库时间戳会让未确认草稿不再展示；退出登记却可能还在。用户只能看到数据库正文，再按 Ctrl+S 可能走干净正文快捷返回，无法处理那份不再可见的未保存内容。
- 同一秒内数据库变化时，新鲜草稿会恢复，但保存的比较基线被替换为重新读取的数据库正文；之后保存可能未经冲突确认就覆盖中间发生的修改。
- 保存请求的不可变编号只存在于编辑器实例中；卸载再挂载后，只恢复正文、不恢复原请求，下一次保存会创建不同编号。
- 禁用切换自动保存时，250毫秒缓存回调执行前直接切换，也未把旧正文写入缓存。
- 大草稿或存储额度受限时，最新内容只在内存，读取函数却优先返回旧的磁盘缓存，遮住内存的新内容。

六项针对性断言在精确4.189.3两个产品文件上失败。基线验证器核对Git blob摘要，拒绝把超时、导入错误或测试环境异常当作复现。

## 修复方式

在现有 `editor:cache:<id>` 草稿中添加版本化的恢复信息：文档标识、编辑前数据库原文、尚未确认的不可变保存请求（如有）、已知冲突状态。没有新增数据库迁移或云端上传。

编辑器缓存实际未确认的正文时，同时记录恢复信息；发出正文请求前也先记录其原编号和原始载荷。成功回执确认后，原有清理只删除与已确认内容匹配的缓存；保存过程中产生的更新正文则带着更新后的基线继续保留。请求超时仍不是回滚。

重新打开时：

1. 有可信格式的保存基线且数据库原文仍匹配：恢复草稿，可以正常自动保存或Ctrl+S，不因经过五分钟而丢弃。
2. 数据库已变化，或者旧版草稿没有可核对的基线：保留并展示草稿，复用已有保存冲突入口；不根据时间戳猜测哪份更“新”，也不自动覆盖数据库。旧版历史缓存可能已无必要，但必须由用户核对，而不是自动写回。
3. 有未确认请求：恢复原编号和不可变载荷，先核对该请求，再处理更新的正文；即使当前显示正文恰好与刚读取的数据库相同，也不能走干净保存或放弃草稿的快捷路径。
4. 请求恢复信息损坏或属于其他文档：不重放该编号，保留可读的草稿文字以供核对，不将损坏响应解释为可自动写入。

切换自动保存关闭时，仍缓存真正的旧草稿，但不擅自发出正文写请求。读取缓存时，本实例已有的内存版本优先，避免磁盘旧值遮住额度受限的新编辑。普通干净笔记不会被新建成草稿。

## 没有改变的规则

普通自动保存和Ctrl+S不新增章节确认步骤。独立引用维护、后端比较写入/终局回执、源码模式、输入法组合、退出握手、同步和数据库schema14保持不变。本次产品修改在前端恢复路径，不改Go后端。

仍不把内存缓存当成磁盘备份：空间不足、正文过大或浏览器存储不可用时，内存保护不能保证强制结束进程后的恢复。未确认内容应单独备份；也不声称修复所有损坏缓存、强制退出、多窗口并发或歧义引用的情形。
