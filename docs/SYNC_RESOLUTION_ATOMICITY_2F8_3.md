# Phase 2F.8.3 — 历史版本与冲突处理回执的事务保护

## 复核范围与缺陷

基线 `7e35b0adc298d1ae233bcad28ef2514c13957625`，上一阶段 Push #1227 的 Linux/Windows 均成功。复核发现两个原有失败路径，故本轮先纠错，不进入新的业务功能阶段。

1. `applyRemoteTx` 忽略覆盖前 `file_versions` 插入的错误，可能丢失历史副本而继续覆盖正文；普通下载和采用远端冲突共用此路径。
2. 上一阶段把远端数据库对象与基线纳入事务，但终态 `sync_conflicts` 更新仍在提交后单独执行；回执失败会留下已覆盖正文、已前移基线和仍待处理的旧冲突。零行更新也曾被当作成功。

## 修复

- 历史版本写入失败或未确认写入一行时，停止覆盖并让调用方回滚；未修改正文/标题的元数据更新不额外制造历史副本。
- 采用远端数据库对象时，在同一 SQLite 事务里核实待处理实例与版本组合、读取基线/本机内容、验证目标结构、保存旧版本、应用内容、更新基线和写入明确选边回执。
- 终态更新必须命中同一个仍为 open 的冲突实例及版本组合，且影响一行；过期、缺失或事务内失效的实例不能授权提交。
- 保留本机以及采用远端附件时，外部动作之后的本机基线与冲突回执也一起提交或回滚。此处不回滚已发布远端清单或附件字节，失败继续由既有恢复协调器保留 `review_required`，不自动重试、不伪报完整回滚。
- 不改变同步版本格式、schema、删除级联、凭据或前端确认协议。

## 测试与负向对照

新增 `resolution_atomicity_test.go`，12 组顶层测试及参数化场景：历史插入 ABORT/IGNORE，普通下载和冲突采用，回执 ABORT/IGNORE，批次后项失败回滚前项与全文索引，删除/标签回执失败，失效实例，事务内迟到退役，发布/附件后的元数据失败与恢复阻断，四种正常选边，取消/只读检查，纯元数据更新，以及无共同基线的首次冲突。

比较全部受保护表中的每一行（正文、目录字段、标签关联、历史、链接、基线和冲突历史），不只比较数量。错误状态遥测和测试触发器定义不算用户数据回滚范围。

为避免“新测试只在新代码上通过”的证据缺口，Linux 增加 `check-sync-resolution-baseline.mjs`：在临时副本里使用精确基线的 engine/validation 源文件，并核验 Git blob SHA，运行新的两组核心故障测试。只有真实编译成功、两组均以指定回归断言失败，才接受负向对照；下载失败、编译失败、超时、测试未运行均不能充当缺陷复现。不重置或修改工作树源文件。

随后当前代码必须通过全部 12 组 Linux race 三轮、原生 Windows 专项和原有全量 CI。原有命令、步骤相对顺序及 18/30 分钟预算不变。
