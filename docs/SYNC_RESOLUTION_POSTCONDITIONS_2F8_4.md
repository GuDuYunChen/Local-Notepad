## 复核发现

上一阶段已经把历史、内容、基线和终态放进同一事务，但对基线/主对象的 SQL 仍只判断返回错误。异常注入中，写入被 `RAISE(IGNORE)` 跳过时，数据库事务可以正常提交，却留下“正文未变或基线未推进，冲突已解决”的错误结果。终态 UPDATE 影响一行，也不保证后续触发器未改变所选方向或其他受保护结果。

本轮先补齐该失败路径，不增加下一业务阶段功能。这不是证明用户现有数据库包含这些触发器，也不是对正常保存普遍失败的断言。

## 修复内容

- 完成所有基线/终态 SQL 后，在同一个事务快照中重读并匹配冲突编号、对象编号、原版本组合、解决状态、所选方向、解决时间及新基线；不把无错误或影响一行当成最终结果正确的唯一证据。
- 采用远端数据库对象时，在终态 SQL 之后、Commit 之前读取实际目标记录，对比完整规范化对象（不只正文），或核实所选永久删除确已生效。
- 删除文件/标签时核实原有规则要求清理的关联行，不添加新级联，不删除无关历史或擅自修复数据。
- 核对失败则回滚本机事务，保留原正文、历史、关联、基线和待处理冲突。
- 核对只读取所选数据库对象及有关元数据，不再次遍历整个工作区、不重复读取附件字节。
- 保留本机/采用远端附件时，仍仅核实本机基线与回执；外部清单或附件已经写入的事实不被伪装为数据库回滚。RecoveryRunner 继续保留待核实状态并阻止未经确认的重放。

## 验证

新增 8 组顶层 `TestResolutionWitness`，共 24 个叶子场景，含主对象/基线跳过、首次冲突无基线、终态后改写、文件/文件夹/标签/标签关联及删除、级联跳过、外部效果后的恢复阻断、正常选边、取消/预演及包含冒号的既有标签关联 ID 兼容。类型专项使用真实 SQLite 事务入口；前两组和外部效果组使用实际 Engine/RecoveryRunner，不混称全部为 HTTP 端到端测试。

Linux 新增精确旧源码对照：只在临时副本替换为 cab7d1c 的 resolution_validation.go，校验 Git blob，要求新增两组故障测试实际编译并分别以指定断言失败。当前源码另外必须通过 race 三轮和原生 Windows 专项。原有全部 CI 门禁、相对顺序、18/30 分钟预算不变。

本地执行了 SQLite 层原有 SQL 的三个异常复现、Go 格式/语法、Node 脚本语法、YAML 门禁保持检查和原始/上传 blob 比对。容器克隆失败于 DNS，工作副本是经过摘要校验的子集；没有在本地运行完整现代 SQLite Go 驱动集成、React 或 Windows 应用。实际引擎负向对照及整仓库验收以本提交 CI/PR 备注为准。

## 边界

该修复核对所选对象、既有删除关联及同步元数据，不是对任意恶意数据库触发器或所有无关表的完整防篡改证明。仍不提供跨设备原子事务、附件字节随 SQLite 回滚、断电或强杀必然恢复保证。不改变普通同步任务的应用算法、远端锁或凭据策略。
