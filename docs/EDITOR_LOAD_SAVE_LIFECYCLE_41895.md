# 4.189.5 — 保存回执与正文重新加载的生命周期隔离

基线 `73c7a680160a1ad1901efb03990b6a03e523577f`（4.189.4 / schema14）。原分支 `feature/knowledge-os-phase2`，Draft PR #2；本轮修复上一阶段，不开始新功能阶段，不合入 master。

## 复查与复现

取得完整源码和已有测试依赖，重建的Git树与基线 `3a0aa2a90c8a85d69b4355eae3c9d3b82b0dc3a6` 完全一致；当前PR也确认该HEAD没有变化。复查聚焦有未确认保存时的重新加载，而不是沿用上一轮“成功保存后重开”的通过结论。

新增10个真实TextEditor测试，精确旧文件的9项断言失败，已有null响应保护作为1项通过对照。失败包括：

- A提交保存后继续编辑，切至B再回A；A的正文尚在加载，保存成功或冲突回执返回时，原实现把用于加载占位的空contentRef写入草稿缓存，覆盖真正的最新草稿。已经排队的后续保存也存在相同的预发送缓存问题。
- 保存回执到达时，正在执行的GET可能已经读取了提交前的正文；不能再用这份旧结果设置恢复基线。
- 卸载会中止当前请求，但原保存函数将中止视作正常返回，排队的后续保存因此继续发出PUT。编辑器消失不应成为继续提交队列的授权。
- 普通正文GET没有应用层超时，也没有核对响应的笔记标识和正文类型；异常响应可能打开错误/空正文，长期无响应则一直停在“加载中”。

新基线验证器核对完整旧文件Git blob，要求准确的九个断言失败和null控制用例通过；超时、语法、导入及运行环境错误不算复现。

## 修复

保存回执仅可更新已完成加载的对应编辑器。正在加载或已经切走的笔记，通过原请求编号核对其缓存归属后更新保存基线/冲突状态，保留最新草稿，不读取空的加载占位正文，不触发当前加载页的onSaved回调。预发送缓存、干净保存快捷路径及结构映射读取也采用相同的已加载文档约束。

每篇笔记记录当前实例已收到的数据库结果修订号。GET期间若收到该笔记的成功或冲突回执，丢弃这份可能过时的读取结果，重新读取；最多3次，持续变化则显示已有的加载失败/重试入口，不无限循环。普通GET复用8秒有界读取，验证返回id和字符串正文，再允许挂载编辑器。超时、格式错误、重试失败都保留原草稿；过时或中止的GET不能更新编辑器。

保存队列绑定编辑器生命周期代数。卸载先撤销本代权限，再中止请求；已经排队的后续动作不会发出新PUT。重开后仍用4.189.4已有的草稿恢复信息核对原请求，再保存更新内容。中止不等于数据库回滚，未确认草稿和退出保护不清空。

## 保持不变

正常自动保存和Ctrl+S不增加章节确认流程；Go事务与回执协议、独立引用维护、缓存格式、退出/源码/输入法保护、同步和schema14均不改。本次无数据库迁移，前后端仍应使用同一分支构建。旧4.189.0不能打开schema14。没有增加新的业务设置或按钮，复用现有加载失败和重试界面。
